Themes across my work

Trade-off analysis

Whether sweeping clock targets in Genus, modeling field weakening in Simulink, or pipelining an FPGA accelerator, I like measuring what each design choice costs in speed, area, power, or torque and then deciding where it stops being worth it.

Trusting the data

End-to-end ownership

Working across layers and with people

I am most interested in physical design and timing, and also in RTL logic design and verification, working on processors and ASICs where logic, layout, and timing meet.

256x16b SRAM Design

18-622 Final Project | Cadence Virtuoso, Spectre | GPDK 45 nm

Overview

The final project for my VLSI course: design a high-performance single-port SRAM with 256 words of 16 bits (4 Kb) in the 45 nm GPDK process. I was responsible for the full schematic and layout, which had to be DRC and LVS clean and meet the specification: access and cycle time under 24 FO4 at the TTLH corner, power under 2.0 mW on a 50/50 read and write mix, a repeated cell area under 1600 λ², total area under 12M λ² with cell area efficiency above 50%, and correct operation in every process corner. The project ran in weekly stages from the cell up to the integrated top level.

What I built and did

  • Week 1, cell design: designed the SRAM cell schematic and laid it out as compactly as the normal logic DRC rules allow. Built a 4x4 array layout to show tiling and contact sharing, extracted the repeat distance, area, and X and Y dimensions, and simulated cell read and write waveforms.
  • Week 2, periphery schematics: designed the decoder, the cell I/O, and the control signal generator at the schematic level, each with wire parasitic models. Integrated them with the cell array into a full schematic of the memory.
  • Week 2, simulation: built dedicated critical path schematics and simulated the read and write critical paths, and simulated the read static noise margin of the cell to check its stability.
  • Week 3, block layouts: laid out the decoder, the cell I/O, and the control signal generator, and brought each to a DRC and LVS clean result. Ran full-schematic read and write simulations of the memory.
  • Top-level integration: integrated the decoder, cell I/O, and control signal generator with the cell array into a complete top-level layout of the memory, and brought it to a DRC and LVS clean result.
  • Verification: ran post-layout extracted simulation of read and write for delay and power across process, voltage, and temperature corners, and checked the design with an extensive testbench covering all possible test vectors.

Results and impact

  • The design meets all of the project constraints at the TTTT, TTLH, and TTHL corners.
  • The extensive testbench covering all possible test vectors passes.
  • Measured values (cell area, access time in FO4, power, and noise margin) will be added to this page.

Skills and tools Cadence Virtuoso, Spectre, SRAM cell design, schematic and layout, wire parasitic modeling, static noise margin analysis, corner simulation, DRC/LVS

RTL-to-GDS Synthesis and PPA Analysis

18-622 VLSI course | Cadence Genus, TCL, Xcelium | Individual lab

Overview

This lab covered the synthesis half of the RTL-to-GDS flow. After running tutorial designs, the main assignment handed me a fixed RTL block with no description. My job was to work out what it did, extract as much power, performance, and area (PPA) from it as I could, and document the trade-offs I found.

What I built and did

  • Identified the block as a pipelined signed 16x16 multiply-accumulate (MAC) unit that accumulates products into a 36-bit register and outputs a saturated 16-bit result with an overflow flag, with a 24-bit control word and valid bit passing through a 16-cycle delay line.
  • Found that the critical path was the multiplier to accumulator adder loop, and used that to decide where the synthesis effort should go.
  • Ran the flow with the provided TCL scripts, changing only the clock constraint and the supplied switches: synthesis effort, voltage-threshold (VT) level, and cost-group weights.
  • Compared low-VT (LVT) and standard-VT cells at a relaxed 100 ns clock, then swept the clock period from 100 ns to 8 ns to 5 ns.
  • At the tightest clock, gave the critical timing group a higher weight so the tool would focus on closing worst negative slack there while limiting area and power growth elsewhere.

Results and impact

  • LVT versus standard VT: the critical path dropped from 9.22 ns to 5.83 ns (about 1.6x faster per full-adder carry) at roughly 5x the leakage. Because leakage was under 3% of total power at a low clock frequency, the penalty was small in absolute terms.
  • 100 ns to 8 ns: the same netlist ran 12.5x faster with the same energy per operation and no meaningful area cost, so the speed was effectively free.
  • 8 ns to 5 ns (200 MHz): the tool replaced ripple-carry adders with carry-lookahead logic and upsized cells, giving about 60% more throughput for about 8.6% more area and 12% more energy per cycle, and the design met timing.
  • Conclusion: the best efficiency is at any period where speed is still free; maximum performance costs a modest area and energy premium at 200 MHz; and leakage-sensitive designs should use standard-VT cells at a slower clock.
  • Limitation I reported: I did not run an equal-weight baseline at 5 ns, so the effect of the group weighting is not isolated from the effect of the tighter clock.

Supporting analyses from the same lab

  • Synthesized an 8-bit adder (about 461 MHz, 252.58 µm², 51.59 µW), then 16-bit (about 400 MHz, 673.66 µm²) and 32-bit (about 412 MHz, 1653.65 µm²) versions, and observed that area and power grow faster than linearly with width.
  • Synthesized my 4-bit combinational datapath from an earlier lab, reaching a minimum area of 55.107 µm² at roughly 2.09 GHz.

Skills and tools Cadence Genus, TCL scripting, logic synthesis, static timing analysis, PPA optimization, gate-level simulation (Xcelium), report writing

Place and Route in Cadence Innovus

18-622 Lab 4 | Cadence Innovus, TCL | Individual lab

Overview

This lab was the implementation half of the RTL-to-GDS flow. After synthesizing the multiply-accumulate (MAC) block in Genus, I took it through placement and routing in Cadence Innovus, studied what each step does to timing, then customized the floorplan and scaled the flow to a 2x2 array of MAC blocks.

What I built and did

  • Ran the full flow step by step (init, place, clock tree synthesis, post-CTS hold fixing, route, and signoff) and summarized what each step does.
  • Compared post-signoff critical path delay, area, and power against the Genus results, and checked for setup and hold violations in the reports.
  • Traced the timing reports after each step to find where the ideal clock assumption is dropped and real clock skew appears, and checked hold timing after signoff.
  • Inspected the layout interactively: the metals used for the power grid, the top metal width, the standard cell row height, and which sides the pins were placed on.
  • Customized the floorplan in the flow's post-init TCL script, changing the pin placement commands to put inputs on the left, outputs on the right, and the clock at the bottom, then measured the effect on delay, power, and area.
  • Scaled the flow to a 2x2 MAC array built from four macros. I assigned pin locations for each macro, brought the clock in at the center of one side, put the A and B inputs on the top and left, put the outputs on the right, and worked to reduce total block area by raising the utilization of the empty space around the macros above the template's roughly 5%. No routing was allowed on metal layers M5 and below inside the macros.

Results and impact

  • The ideal clock assumption disappears at clock tree synthesis, and hold timing has to be checked afterward because real skew can create violations that synthesis never showed.
  • I treated floorplan choices such as pin placement and macro orientation as part of the PPA result, since they change wire length, area, and routing.

Skills and tools Cadence Innovus, TCL scripting, floorplanning, clock tree synthesis, static timing analysis, hold fixing, PPA analysis

Assertion-Based Verification of Encrypted Calculator IP

18-341 Project 4 | SystemVerilog, SVA, Synopsys VCS, DVE

Overview

I was given an encrypted reverse polish notation (RPN) calculator as a black box and asked to verify it, with no golden or reference model allowed. The design has an 8-entry stack, four commands (START, ENTER, ARITH_OP, DONE), six operations (add, subtract, and, swap, negate, pop), and four error outputs (stackOverflow, unexpectedDone, dataOverflow, protocolError). All the checking had to come from assertions and from the test values I chose, so the work was to decide what correct behavior is and encode it.

What I built and did

  • Wrote about 1,100 lines of SystemVerilog in the testbench: 36 concurrent assertions built from 28 properties, one immediate assertion for the post-reset check, and 32 directed test tasks.
  • Used SVA implications (|-> and |=>), property local variables, parameterized properties, and disable iff for reset.
  • Built a protocol and stack-depth tracker, a small FSM that predicts which error should fire without copying stack values, and kept one-cycle-old sampled copies so error messages report the values from the failing cycle.
  • Organized tests into four groups: initial behavior (handout waveforms, DONE edge cases, ignored inputs); stack (walking ones and zeros across all 8 places, overflow on the ninth push, every operation on a full stack); arithmetic (carry and borrow chains, both sides of every overflow boundary); and protocol (every unused operation bit, every invalid command, errors after errors, reset in the middle of a calculation).
  • Wrote a 10-category fault model to guide which bugs the assertions and tests had to be able to catch.

Results and impact

  • Zero assertion failures on the fault-free model, so the checks did not raise false alarms.
  • Detected faults in all 7 faulty design variants, for example an adder dropping the carry from bit 11 to bit 12, negate computing one's complement, swap acting as a no-op, protocolError not held until DONE, missing item-count error checks, and DONE being ignored with more than one item on the stack.
  • The last variant (Phase 2) took longer, and I resolved it by debugging with a TA.

Skills and tools SystemVerilog, SVA (concurrent and immediate assertions), Synopsys VCS, DVE waveform viewer, fault modeling, Git

Network on Chip (NoC)

18-341 Digital Systems | SystemVerilog, VCS | Individual project, two parts

Overview

I designed the core components of a simple network on chip: nodes that inject and receive packets, and routers that move packets between them. The topology had two routers connecting six nodes, with testbenches standing in for the components sending and receiving messages. The goal was to deliver every packet correctly, then to make the network fast and fair.

What I built and did

  • Wrote a Node module and a hardware FIFO queue to buffer 32-bit packets (source, destination, and 24 bits of data) coming from a testbench and send them into the network one byte at a time using a ready/valid style handshake.
  • Wrote a Router with four ports that reassembles incoming bytes into packets, decides which output port each packet needs, and forwards it, using concurrent finite-state machines at the FSM-D level of modeling.
  • Handled two different transfer widths: 32-bit word transfers between the testbench and nodes, and 8-bit byte-serial transfers between nodes and routers and between the two routers.
  • Moved beyond one transfer per clock so that independent packets (for example, port 0 to port 2 and port 2 to port 1) could move at the same time.
  • Added round-robin priority so that no input port could be starved when several packets competed for the same output.

Results and impact

  • Completed both parts and passed every provided test category: single-packet transfers within and across routers, simultaneous concurrent transfers, source and destination stress tests, fairness, and a performance benchmark.
  • Kept the router within the limited storage budget while still delivering all packets without loss.
  • The project taught me how fixing one bottleneck (serialized transfers) exposes the next one (starvation), and how to reason about fairness and throughput together.

Skills and tools SystemVerilog, FSM design, FIFO design, arbitration and fairness logic, packed structs and arrays, VCS simulation, functional and performance verification, Git

Matrix Multiply Accelerator

18-341 Digital Systems | SystemVerilog, Vivado | Xilinx Spartan-7 (Boolean Board)

Overview

This project explored the special hardware features inside a modern FPGA. The task was to compute Y = A x B + C, where A is a 128x128 matrix of 8-bit values, B is an 8-bit vector, C is a 16-bit vector, and Y is a 32-bit vector, then display the sum of Y on the board. The design had to meet a 100 MHz clock and finish in as few clock cycles as possible.

What I built and did

  • Designed a pipelined accelerator in SystemVerilog that used the FPGA's dual-port block RAM and hardware multiplier blocks to run many multiply-accumulate operations in parallel.
  • Used generate statements to instantiate multiple memories and multipliers, and organized the data so computations could run concurrently.
  • Handled the block RAM's registered-address behavior, where data appears a cycle after the address is presented, when building the pipeline.
  • Used Vivado static timing analysis to find the longest register-to-register paths and broke large blocks of logic into pipeline stages.

Results and impact

  • Met the 100 MHz timing requirement with a positive worst negative slack.
  • Completed the full calculation in under 512 clock cycles, which was the assignment's stated speed target.
  • Kept all intermediate values at full width so that the speed gain did not cost accuracy.

Skills and tools SystemVerilog, Vivado, static timing analysis, pipelining, block RAM and multiplier IP, FPGA design, performance optimization

Cache Simulator and Matrix Transpose

18-213 Cache Lab | C, Git | Individual project

Overview

This project had two parts: write a cache simulator in C, then write a matrix transpose function that runs as few cycles as possible against a simulated cache. It is the project where I learned how cache design decisions show up directly in code performance.

What I built and did

  • Wrote a command-line cache simulator in C that takes the number of set index bits, lines per set, and block bits, then processes a memory trace file. It uses LRU replacement and a write-back, write-allocate policy, and reports hits, misses, evictions, and dirty bytes.
  • Parsed options with getopt and trace lines with fgets and strtoul, and handled bad or missing arguments with the same error messages as the reference simulator.
  • Wrote my own short memory traces that produce exact hit, miss, and eviction counts within a small operation limit, to confirm I understood the cache behavior.
  • Optimized a matrix transpose function against a simulated cache, with a separate target for each matrix size.

Results and impact

  • The simulator matched the reference simulator on every test trace.
  • The transpose took 35,456 cycles for a 32x32 matrix and 33,881,344 cycles for a 1024x1024 matrix, both under the full-credit thresholds of 36,000 and 35,100,000.

Skills and tools C, cache memory systems, memory hierarchy optimization, command-line tools, Git

Overview

In this project I implemented a virtual machine in C that executes compiled C0 programs. It is a stack-based machine, so every instruction reads its operands from an operand stack and pushes its result back.

What I built and did

  • Implemented the instruction fetch and decode loop that executes bytecode instructions for arithmetic, control flow, memory operations, and function calls.
  • Managed the operand stack and function call frames so that nested calls and returns work correctly.
  • Worked with low-level C memory handling and pointers, which connects directly to how real processors execute instructions.

Results and impact

  • Gained a concrete understanding of how a processor-like machine executes a program one instruction at a time.
  • Strengthened my C programming and debugging skills on a systems-level task.

Skills and tools C, systems programming, stack-based virtual machines, pointers and memory management, debugging
